# PPT 助手

将用户本次指定的材料整理成有来源、可编辑的演示文稿。项目知识保存在目标项目中；插件提供通用的汇报、版式、制作和检查规则。

## 开始与恢复

1. 确定目标项目、材料范围、汇报目的、听众、时长或页数、指定模板。已有任务先读取运行状态与审阅记录。仅追问影响方向的缺口。
2. 插件根是本文件所在目录的上两级。使用实际可用的 Python 与 Node，先查 `scripts/ppt_drawer.py --help`；解析和阶段命令见[运行接口](references/runtime.md)。原始材料保持为来源，在项目中创建运行产物。
3. 阅读[协作入口](references/roles.md)，用宿主真实的子 agent 工具按职责调度。给每个角色明确的项目、run、输入、输出和完成条件，记录真实 agent ID 与交接证据。调度能力缺失时说明缺口，不伪造已执行的子 agent。

## 从材料到样稿

4. 领域分析角色按[知识与来源规则](references/knowledge.md)建立项目知识库、素材索引与补充知识清单。读取失败、信息冲突和缺失结果均保留具体说明。
5. 汇报策划角色形成整稿大纲与逐页目的；版式设计角色按[风格选择](references/visual.md)安排证据和视觉层级。页面方案合同见[页面方案](references/plan.md)。
6. 由唯一的 PPT 制作角色通过工作流 `render --stage sample` 制作三页代表性样稿。质量检查角色检查样稿和来源，制作角色修复对应问题。
7. 提交大纲、模板选择理由、三页样稿与预览、当阶段的补充知识清单。按[阶段复盘](references/retro.md)记录发现和验证状态，然后等待用户审阅。

## 从确认到整稿

8. 用户明确确认当前大纲与样稿后，将实际确认原文交给工作流 `approve`。确认由运行时绑定当前材料、方案和样稿；内容、模板或样稿改变后重新检查审阅状态。历史任务的确认与模型生成的确认均不能代替本次用户意见。
9. 用工作流 `render --stage full` 制作整稿。完整稿通过同一制作入口，其他角色提供方案或问题清单。质量检查涵盖来源、覆盖情况、模板差异、遮挡、文本溢出、图像比例和原生对象。
10. 修复后复查受影响页，通过 `retro` 与 `finish` 留下有证据的阶段记录。交付可编辑 PPTX、预览、补充知识清单及影响使用的待补事项。失败结束也按复盘规则记录可继续的位置。

样稿阶段已获用户确认后可按其意见继续；用户要求先看样稿时保持审阅阶段。已有原始数据的图表制作成原生对象；仅有论文图片时保留清晰图片，说明和标注独立可编辑。
